## 故障结论

目标设备是 x86_64 OpenWrt 24.10.0，使用定制内核 `6.12.16` 和 fw3/iptables legacy。TUN 可用，但 nftables Netlink 查询返回 `EINVAL`。原配置强制 `auto_redirect: true`，因此 sing-box 已创建 TUN、启动 SOCKS 监听后，仍会在 post-start 阶段退出。

当前项目原本已有 OpenWrt 包管理器与模块准备代码。源头项目 `/data/projects/iVnc-Org/miao-offical` 已将依赖检查放入共享的内核启动函数，但 Linux 配置仍强制启用 `auto_redirect`，并安装 `kmod-tun`、`kmod-nft-queue`。直接移植这部分代码不能解决目标设备缺少 nftables 的问题。

设备的软件源对应官方 `6.6.73` 内核，与运行内核不匹配。此次利用已有 TUN 运行兼容策略路由，没有在设备安装模块、强制忽略依赖或修改持久防火墙配置。

## 2026-11-24：树莓派 5 启动与资源清理

目标设备为 aarch64 的树莓派 5，运行 ImmortalWrt 25.12.2、内核 6.12.103。这次确认了两个独立缺陷：

1. `/sbin/fw3 -> fw4` 是兼容链接，设备实际运行原生 fw4，未安装 iptables。旧判断只检查 `fw3` 是否存在，错误要求 iptables。现改为比较实际文件身份，兼容符号链接和硬链接；真正的旧 fw3 路径保持原行为。配置变更也在停止现有服务前检查必需工具。
2. 设备 BusyBox `ip` 拒绝 `table 2022` 和随机大编号表的查询、删除命令；大表号的显示也不能可靠地作为数字解析。这导致停止后遗留归属记录，并使再次启动报 `ROUTE_CLEANUP_FAILED`。现通过 Netlink 记录内核原始规则和完整表号，精确回收自有规则及随机表内的本地回环路由，兼容已删除资源和旧记录。

## 2026-11-25：Tailscale 上游选路修复与整体复核

真实上游是经 `tailscale0` 到达的 SOCKS 节点，地址属于 `100.64.0.0/10`，内核通过策略表 52 选路；WAN 默认出口是 `eth0`。`route.auto_detect_interface: true` 的含义是默认绑定默认网卡，并非按每个目标查询完整策略路由。它把该节点的连接错误绑定到 WAN，导致 Miao SOCKS、DNS 和透明出网一起超时。

使用同一核心、同一节点的独立 SOCKS 实例做了对比，未启用 TUN：默认网卡绑定超时，关闭默认绑定与显式绑定 `tailscale0` 均返回 gstatic HTTP 204。随后真实 TUN 接管也在关闭默认绑定后恢复。本次无需修改 Tailscale 标记、全局策略路由、防火墙持久配置或硬件卸载设置。

## 2026-11-25：Wi-Fi 的 Google 首页失败，确认 DNS 接管缺口

修复前存在阻塞完整 Google 网站访问的问题。此前把 `www.gstatic.com/generate_204` 的通过结果概括成 Google 验证，覆盖范围不足；相关历史文字已更正。以下为修复前直接测试 Google 首页、跳转域名和真实 Wi-Fi 客户端路径的故障证据。

| 证据 | 实际结果 |
| --- | --- |
| 路由器 dnsmasq 查询 `www.google.com` | A 为 `69.171.235.22`，AAAA 为异常的 `2001::1`；缓存 A 的剩余 TTL 曾为 1833 秒 |
| 查询上级 DNS `192.168.1.1` | 返回另一异常 A `185.45.5.35`，AAAA 同样为 `2001::1` |
| 通过 Miao DNS 引擎查询 | `1.1.1.1:53` 的查询被核心处理，日志确认上游 DNS 经 SOCKS TCP；得到 `142.251.150.119` 等正常结果 |
| 默认透明访问 `https://www.google.com/` | 实际目标为 `69.171.235.22:443`，TLS 未完成，超时 |
| 同一节点通过 SOCKS 按域名访问 | 跟随 `www.google.com` 到 `www.google.com.hk`，TLS 验证及最终 HTTP 200 成功 |
| 透明访问并用 `--resolve` 指定正常 Google 地址 | 保持 URL、Host 和 TLS 域名校验，指定 `108.177.97.138` 后 HTTP 200 成功 |
| 真实 Wi-Fi 客户端 | 日志确认 `192.168.11.216` 和 `192.168.11.117` 的连接已被 TUN 接管，但出站仍指向错误的 `69.171.235.22:443` |
| ipinfo | 透明访问 HTTP 200，与用户观察到海外代理出口一致 |

流量代理与 DNS 形成了两条路径：网页 TCP 已走 Miao 的代理节点，Wi-Fi 的默认 DNS 仍由原 dnsmasq 处理。运行中的 dnsmasq 使用 `/tmp/resolv.conf.d/resolv.conf.auto`，上游为 WAN 获得的 `192.168.1.1`。该地址处于本地 WAN 子网，绕过透明接管，因此没有进入 Miao 的受保护 DNS。路由器自己的系统解析还使用 Tailscale MagicDNS，这也不等于自动使用 Miao DNS。

ImmortalWrt 的 `inet dnsmasq` 表另有 `DNSMASQ HIJACK`，将收到的 UDP/53 重定向至 dnsmasq。其 prerouting 优先级为 -95，Miao 的 NAT/UDP 链分别为 -99/-98；DNS 重定向仍会在最终路由判断前生效。只在 sing-box 中配置 `hijack-dns` 和代理 DNS，不能保证送往路由器 dnsmasq 的查询也获得保护。

dnsmasq 还配置了 `min-cache-ttl=3600`，错误记录会被长期保留。启动或重启 Miao 并不会自动清理 dnsmasq 和浏览器已有缓存。当前 `ipv4_only` 仅作用于 Miao 自己处理的 DNS，无法过滤这条 dnsmasq 路径返回的异常 AAAA。

修复应把 OpenWrt 的 DNS 一并接入生命周期：为 Miao 提供本地 DNS 服务，将 dnsmasq 的互联网查询送入该服务，保留本地域名与 DHCP 解析；处理现有 DNS 重定向，避免查询绕回旧上游；切换后清理旧缓存；停止、失败及管理器异常退出时恢复原解析，防止留下不可用的 DNS 服务器。验收必须包含 `www.google.com` 与跳转域名的 DNS、真实 HTTPS 首页，以及 Wi-Fi 客户端路径，不能只使用 gstatic 的 204。

该诊断阶段未修改线上 DNS、DHCP 或防火墙配置，Miao 保持运行。构建主机记录位于 `/tmp/miao-pi5-session/google-root-initial.json`、`google-follow-initial.json`、`google-relevant-flows.log`，日志中的节点信息已隐藏。

后续已完成 [DNS 修复方案与验收](openwrt-dns-fix-plan.md)，包含真实 dnsmasq 2.93 的独立实验、生命周期恢复要求与实施结果，最终复核如下。

### 整体 review 发现与处理

| 复核发现 | 处理与验证 |
| --- | --- |
| 只保护 dnsmasq，路由器默认的 Tailscale DNS 仍返回污染结果 | 对系统解析器的 UDP/TCP、IPv4/IPv6 查询建立自有 nft 表，保留核心引导 DNS 和 Tailscale 基础连接；逐项探测后才发布就绪 |
| IPv6 DNS 在到达 NAT 之前被核心的严格路由规则拒绝 | 提前标记应用 DNS，在 NAT 阶段区分应用查询与核心带标记的连接；隔离 IPv6 UDP/TCP 与真机默认解析通过 |
| dnsmasq 忽略部分 Tailscale 来源的回环查询，Tailscale 输入链也拒绝相关回复 | 将重定向查询的来源转换为回环地址，添加仅匹配本次 conntrack DNS 回复的归属例外；保留 `local-service`，停止后撤销例外，链重建后自动补齐 |
| 启动期间 `/etc/resolv.conf` 重新生成，引发指纹变化和安全拒绝 | 在写入系统配置之前完整复检一次，使用通过复检的最新解析器；服务身份变化、竞争上游和持续变化继续拒绝。模拟良性重生成通过，模拟新增竞争上游正确拒绝，实机重复启动通过 |
| DNS 就绪探测早于历史节点恢复，可能先使用不可达的首节点 | 在生成、缓存恢复和旧运行配置准备时固定保存的选择，保持路由清单哈希一致；首节点故意不可达的夹具通过 |
| 管理器 SIGKILL 后，核心偶尔留下策略规则，DNS 恢复不足以完成联网恢复 | 独立守护确认核心退出后，回收归属记录中的路由、nft 表和 fw3 规则；明确传递运行目录，验证重启管理器之前已恢复基线 |
| 清理其他资源失败时可能重复重启已恢复的 dnsmasq | 写入恢复进度，后续只重试未完成的资源清理；归属冲突保留记录并报告，不覆盖外部内容 |
| 停止失败仍关闭核心或保存已停止状态 | DNS 恢复失败时保留活核心，错误贯穿网页、配置更新、CLI 与升级入口；故障解除后可重试停止 |
| 测试代理池端口与 DNS 探针的临时连接端口偶发重叠 | 夹具使用低于临时端口范围的固定监听端口，保留真实端口冲突与回滚验收 |
